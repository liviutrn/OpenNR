# Public DLSS5 portable checkpoint: current-clone Skyrim recheck

Date: 2026-09-12  
Decision status: useful research baseline; not a native-DLSS5 replacement and not promoted to OpenNR runtime  
Promotion: `false`

## Executive result

The new public repository is relevant to OpenNR-VR because it publishes a
complete, ordinary-PyTorch native-output distillation workflow: a small model,
a distributable checkpoint, and a training script. That is a real methodology
milestone.

The supplied checkpoint itself did not transfer to the retained Skyrim
teacher pairs. On one existing full-eye temporal sequence, using all 16 frames
and both eyes (32 full-eye samples), it was finite but worse than returning the
captured RGB input unchanged on every sample:

```text
identity MAE:       0.0188294710
portable MAE:       0.0216407970
portable regression: +0.0028113253
better samples:     0 / 32
```

This is a substantial enough regression that it is not explained by a tiny
quantization or timing issue. It says the shipped checkpoint is a synthetic
or upstream-domain residual fit, not an already useful Skyrim/OpenNR teacher
surrogate.

The architecture remains worth retaining as a fast baseline. On the local
RTX 5070 Ti, with the input tensor already resident on the GPU, one full-eye
`2496x2688` inference measured:

| Execution | Median | p95 | Scope |
|---|---:|---:|---|
| PyTorch FP32 | 24.197 ms/eye | 24.239 ms/eye | model-only, input already on device |
| PyTorch FP16 | 14.057 ms/eye | 14.065 ms/eye | model-only, input already on device |
| TensorRT fixed-shape control | 7.48 ms/eye | 10.11 ms/eye | earlier isolated control, same model family |

Serial FP16 stereo would be approximately `28.1 ms` for the model alone.
That is not a VR-ready end-to-end result. It excludes input conversion,
Feature 18 resource preparation, copies/interop, synchronization, compositor,
SteamVR, and headset frame pacing. The TensorRT number is a portability
control, not a live OpenNR integration result.

## What was tested

The isolated source snapshot is:

```text
repository: https://github.com/taowen/dlss5-as-inpainting
commit:    59a414cfd09676f3a09ff042330b5dc8407ebc79
clone:     C:\OpenNR\research\public_dlss5_as_inpainting_20260912
checkpoint: models\dlss5_pytorch_portable_v1.pt
checkpoint SHA256: b05d921c3ae7a4579eac5c8538c1e0834d7a9613ea296fae0ee5c08cc811f6c6
```

The checkpoint is an ordinary `DLSS5PortableModel` with 12,739 parameters:
three 3x3 convolutions, 32 hidden channels, SiLU activations, a residual
output, and clamping. The checked-in model metadata reports 250 synthetic
distillation steps, RGB-only training, and optional depth/history/motion
channels present in the API but not calibrated by that training run.

The test used the retained OpenNR sequence:

```text
C:\OpenNR_Captures_FullEyeTemporalStateTranche_20260910\seq-1789071762719-5
```

It evaluated `frame_00000001` through `frame_00000016`, eyes 0 and 1, at
`2496x2688`. OpenNR's retained `input_*.raw.bin` and `teacher_*.raw.bin`
files are packed RGBA8 (`width * height * 4` bytes), not the RGBA16F format
expected by the upstream helper. The probe therefore normalized the captured
RGB8 bytes by 255 and compared the portable output with the native teacher in
that same RGB code domain. This is a valid transfer diagnostic with a clean
identity baseline, but not a formal RGBA16F native-contract equivalence test.

The checkpoint was loaded with `torch.load(..., weights_only=True)`. The
repository's native NVIDIA DLL and CUBIN files were not executed, installed,
or copied into OpenNR/MGO.

## Why this is still relevant

The release proves three useful things for OpenNR:

1. A native-output distillation pipeline can be expressed as ordinary
   portable PyTorch rather than requiring the recovered 71-block graph.
2. A very small model can be exported and accelerated with ordinary ONNX and
   TensorRT tooling.
3. The correct experiment is to train a new student on the target game's
   native input/output pairs, not to assume a public synthetic checkpoint will
   transfer.

It does not prove that the supplied checkpoint is a DLSS5 clone. It has no
recurrent state, history update, motion-based reprojection, stereo coupling,
or long-range context. Its three stacked 3x3 convolutions provide only a
small local receptive field. It therefore cannot replace the native Feature
18 contract merely because its function signature accepts depth, history,
motion, and a mask.

The repository also contains a native NVIDIA DLL and extracted CUBINs in the
current public snapshot. Those are materially interesting for static kernel
inventory, but they are vendor/runtime artifacts rather than an owned,
portable OpenNR implementation. They were kept isolated and not executed.
The snapshot has no discoverable top-level `LICENSE`, `NOTICE`, or `COPYING`
file, so redistribution and packaging of those native artifacts remains
unresolved.

## Recommendation

Do not collect more Skyrim data merely to make the supplied checkpoint work;
the current evidence already rejects it as a drop-in model. Do not wire its
optional guide inputs into OpenNR either: the shipped checkpoint was trained
without those conditions, and the earlier broad OpenNR assessment found that
adding available depth/motion guides made error worse.

If we want to pursue this route, the worthwhile follow-up is a new isolated
OpenNR student using the same tiny architecture or a modestly larger variant:

- train from scratch on exact native OpenNR input/teacher pairs;
- start RGB-only so the baseline has a well-defined contract;
- retain the identity, public-checkpoint, and new-student lineages separately;
- select on sequence-disjoint validation and report frozen full-eye test data;
- then add history/motion only with a separately trained, audited contract;
- benchmark fixed-shape TensorRT and the complete two-eye path before any
  runtime work.

Existing retained pairs are sufficient for that bounded pilot. If the RGB-only
pilot shows a real held-out gain, then collect more native data—especially
sequence-disjoint full-eye temporal runs with lossless/float input and output,
exact reset metadata, native motion, depth, and both eyes. New data should be
spent only after the architecture demonstrates a gain over identity on the
existing frozen split.

This makes the public release a useful method and speed baseline, not a reason
to replace the current OpenNR teacher or to declare the recovered weights
unusable.
